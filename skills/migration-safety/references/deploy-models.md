# Модели деплоя и обратная совместимость

Один и тот же DDL имеет разный риск в зависимости от модели деплоя. Это первое,
что нужно установить.

## Короткий downtime (стоп → миграция → старт)

Сервис останавливается, миграция применяется, сервис запускается. Старый и новый
код одновременно **не** работают.

- Обратная совместимость схемы **не критична**.
- Главный риск — **длительность блокировки**: пока идёт rewrite/долгий
  `CREATE INDEX`, сервис лежит. Оценивать на объёме прода; тяжёлые операции —
  через `CONCURRENTLY`/батчи, чтобы окно было предсказуемым.
- `RENAME`/`DROP` относительно безопасны (никто не обращается к схеме), но
  необратимы по данным — нужен бэкап.

## Zero-downtime / rolling

Во время выката работают **обе** версии кода против **одной** схемы. Любое
несовместимое изменение ломает старый (или новый) код.

Правило: **схема совместима и со старым, и с новым кодом** на протяжении выката →
паттерн expand/contract.

### Expand / contract (переименование `amount` → `total`)

1. **Expand (миграция №1):** добавить `total` (nullable, без тяжёлого default).
   Старый код её игнорирует.
2. **Код:** деплой версии, которая пишет в **обе** колонки и читает из новой (с
   фолбэком). Дождаться полного выката.
3. **Backfill:** заполнить `total` из `amount` батчами (вне транзакции).
4. **Код:** деплой версии, использующей только `total`.
5. **Contract (миграция №2, после выката):** убрать двойную запись, удалить
   `amount`.

Тот же приём — для смены типа, разбиения/слияния колонок, новых `NOT NULL`.

### Что нельзя одной миграцией при zero-downtime

- `RENAME` колонки/таблицы.
- `DROP COLUMN`/`DROP TABLE` до отказа кода.
- Новый `NOT NULL`/`UNIQUE`/FK без двухфазного приёма и backfill.
- Сужение типа/ограничения, под которое не подходят данные.

## «По-разному»

Если модель деплоя не фиксирована — определить по контексту (балансировщик/
несколько воркеров/graceful reload или просто `systemctl restart`). При сомнении
оценивать по **более строгой** (zero-downtime) модели: совместимые миграции
безопасны в обоих режимах, обратное неверно.

## SQLite и переезд на Postgres

- **Урезанный `ALTER`**: `ADD COLUMN`, `RENAME`, `DROP COLUMN` (3.35+). Смена типа
  и большинство constraint — через пересоздание таблицы (медленно, блокирует,
  писатель один).
- **Слабая типизация/неэнфорсимые constraint** (FK по умолчанию выключены).

Сигналы «пора на Postgres» (до роста данных): конкурентная запись, table-rebuild
занимает заметное время, нужны строгие constraint/partial-индексы/`CONCURRENTLY`.
При переезде проверить данные на нарушения будущих constraint (NULL под `NOT NULL`,
дубликаты под `UNIQUE`, «висячие» FK).

## Чек-лист

- [ ] Модель деплоя определена (или взята более строгая).
- [ ] Схема совместима со старым кодом (zero-downtime).
- [ ] Expand и contract — отдельными миграциями.
- [ ] Backfill — батчами, вне транзакции, между фазами.
- [ ] SQLite-нюансы учтены; при необходимости — план переезда.
