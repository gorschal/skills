# Git Commits

Планирование и выполнение атомарных коммитов, когда изменений много и они из
разных областей. Для двух-трёх связанных правок план избыточен — коммить сразу.

> Формат сообщений — **Conventional Commits** (см. reference), но приоритет у
> конвенции проекта, если она задана. Версия/CHANGELOG/тег — вне scope.

## Когда применять

- «Сделай коммиты, проанализировав изменения», «разбей на логические коммиты».
- В дереве много staged/unstaged/untracked файлов из разных областей.

## Принципы

1. **Атомарность:** один коммит — одно логическое изменение.
2. **Резать по границам смысла**, а не по типам файлов. Главный критерий —
   **«что захочется откатить как единое целое»**.
3. **Каждый коммит оставляет дерево рабочим** (собирается, тесты проходят).
4. **Жёсткая зависимость** — файлы, порознь ломающие проект, идут в один коммит.
5. **Сообщения — в стиле репозитория** (`git log`), а не абстрактно «правильно».

## Процесс

### 1. Состояние репозитория

```bash
git status --porcelain
git ls-files --others --exclude-standard
git log --oneline -10        # стиль сообщений, принятый в репо
```

### 2. Группировка

По убыванию приоритета:

1. **Фича/модуль** — изменения, которые вместе имеют смысл и вместе ломаются.
2. **Тип изменения** — docs, feat, refactor, fix, test, config.
3. **Жёсткая зависимость** — обязательно вместе.

### 3. Порядок

От фундамента к листьям, чтобы дерево оставалось рабочим:

```
документация/конфиг → инфраструктура/ядро → новые модули →
изменения существующих модулей → тесты → шаблоны/статика → мелкие правки
```

Django: settings/зависимости → ядро → по коммиту на приложение → шаблоны/статика.

### 4. План

Нумерованный список: заголовок коммита, файлы, готовая команда, однострочное
обоснование группировки. В конце — сколько коммитов и по какому принципу разрезано.

### 5. Выполнение

После одобрения плана — **автономно**, без подтверждения на каждый `git add`.
После каждого коммита `git status --short`; в конце дерево чистое.

Подробно: [references/planning.md](references/planning.md).

## Ветвление

Именование: `<тип>/<краткое-описание>` или `<тип>/<номер-задачи>-<описание>`.

```
feat/aneepay-123-auth-google
fix/empty-cart-checkout
docs/update-contributing
```

`main` — защищённая ветка: прямой push запрещён; изменения попадают только через
PR после прохождения CI и ревью.

Подробно: [references/branching.md](references/branching.md).

## Формат сообщений

```
<тип>(<scope>): <описание в инфинитиве>
```

- `scope` — подсистема монорепозитория: `django`, `fastapi`, `foundry`, `bdd`,
  `docker`, `ci`, `deps`.
- Описание — **в инфинитиве** («что сделать?»): «настроить», «устранить»;
  строчными буквами, без точки в конце.
- Типы: `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`, `revert`
  (CI/сборка/зависимости — под `chore`).
- Тело — «почему»; футер — `Closes: <задача>`, `Co-authored-by:` при необходимости.
- Язык subject — русский (как в репозитории).

Как надо: `fix(django): устранить утечку памяти на главной странице`,
`test(bdd): уточнить шаг ретрая вебхука`.

Как не надо: `fix: Исправил баг.` (заглавная, прошедшее время, точка),
`feat: добавляет авторизацию` (настоящее время), `правки` (без типа).

Подробно: [references/conventional-commits.md](references/conventional-commits.md).

## Особые случаи

- **`MM` / `AM`** — у файла есть и staged-, и unstaged-часть: решить, входит ли
  unstaged в этот коммит, не стейджить вслепую.
- **`??`** — добавить, внести в `.gitignore` или удалить; мусор в коммит не
  попадает молча.
- **Много новых файлов** (шаблоны, статика) — крупный коммит допустим, но
  группировать по функциональным областям.
- **Не коммитить**: отладочный вывод, закомментированный код, локальные конфиги,
  секреты/`.env` — назвать отдельно, не прятать в общую группу.

## Границы

- Только планирование и выполнение коммитов.
- Версия, CHANGELOG, тег релиза — вне scope.
- Ревью содержимого изменений перед коммитом — отдельная задача (code review).

## Чек-лист

- [ ] `git status --porcelain` и `git log` просмотрены.
- [ ] Изменения сгруппированы по смыслу, не по типам файлов.
- [ ] Каждый коммит атомарен и оставляет дерево рабочим.
- [ ] Порядок — от фундамента к листьям.
- [ ] Сообщения в стиле репозитория; тип/scope корректны.
- [ ] Ветка названа по схеме `<тип>/...`; в `main` — только через PR.
- [ ] Секреты/`.env`/мусор не закоммичены.
- [ ] После выполнения дерево чистое.
