# Ветвление

## Именование

Схема: `<тип>/<краткое-описание>` или `<тип>/<номер-задачи>-<описание>`.

```
feat/aneepay-123-auth-google
fix/empty-cart-checkout
docs/update-contributing
```

- `<тип>` — тот же набор, что у коммитов (`feat`, `fix`, `docs`, `chore`, ...).
- Описание — короткое, kebab-case, по-английски (как в примерах).
- Номер задачи — если есть трекер (`aneepay-123`).

## `main` — защищённая ветка

- Прямой push в `main` **запрещён**.
- Изменения попадают только через **PR** после прохождения **CI** и **ревью**.

## Поток работы

1. Ветка от `main` по схеме именования.
2. Атомарные коммиты (см. `planning.md`, `conventional-commits.md`).
3. Push ветки, открыть PR.
4. CI зелёный + ревью → merge в `main`.

## Правила

- Одна ветка — одна задача/фича; не смешивать несвязанные изменения.
- Не коммитить напрямую в `main`.
- Перед PR — локальные линт/тесты/типы.
- Не делать force-push в общие ветки без необходимости.

## Антипаттерны

| ❌                               | ✅                   |
| -------------------------------- | -------------------- |
| Push напрямую в `main`           | PR после CI и ревью  |
| `mybranch`, `test`, `fix2`       | `<тип>/<описание>`   |
| Ветка с кучей несвязанных правок | одна задача на ветку |
| PR без зелёного CI               | дождаться CI         |
| Force-push в общую ветку         | обычный push/merge   |

## Чек-лист

- [ ] Ветка названа по схеме `<тип>/<описание>`.
- [ ] Ветка — под одну задачу.
- [ ] В `main` — только через PR.
- [ ] CI и ревью пройдены перед merge.
