# Планирование коммитов

## 1. Состояние

```bash
git status --porcelain
git ls-files --others --exclude-standard
git log --oneline -10
```

- `--porcelain` — машинно-читаемый статус (XY: `M`, `A`, `D`, `??`).
- `ls-files --others` — untracked.
- `git log` — **стиль сообщений этого репозитория** (важнее абстрактной «правильности»).

## 2. Группировка

Резать **по границам смысла**, а не по типам файлов. Главный критерий:
**«что захочется откатить как единое целое»**.

По убыванию:

1. **Фича/модуль** — изменения, которые вместе имеют смысл и вместе ломаются.
2. **Тип изменения** — docs, feat, refactor, fix, test, config.
3. **Жёсткая зависимость** — файлы, порознь ломающие проект, идут в один коммит
   обязательно.

Примеры разрезов:

- Django: `settings`/зависимости → ядро → по коммиту на приложение → шаблоны/статика.
- FastAPI: конфиг → домен → роутеры/сервисы/репозитории по модулю → тесты.
- Node: package-файлы → тулинг → исходники по фичам → стили → тесты.

## 3. Порядок

От фундамента к листьям, чтобы **каждый коммит оставлял дерево рабочим**:

```
документация и конфигурация → инфраструктура и ядро → новые модули →
изменения существующих модулей → тесты → шаблоны и статика → мелкие правки
```

## 4. Шаблон плана

```markdown
## План коммитов

1. `docs: обновить README и ADR-0002`
   - `README.md`, `docs/adr/0002-*.md`
   - `git add README.md docs/adr/0002-*.md && git commit -m "docs: обновить README и ADR-0002"`
   - Обоснование: документация независима от кода.

2. `feat(payment): добавить экспорт метрик аккаунта`
   - `payment/exporters.py`, `payment/views.py`, `payment/urls.py`
   - `git add payment/exporters.py payment/views.py payment/urls.py && git commit -m "..."`
   - Обоснование: новая фича одного модуля, вместе ломается/работает.

3. `test(payment): покрыть экспорт метрик`
   - `payment/tests/test_exporters.py`
   - ...
   - Обоснование: тесты следуют за кодом.

**Итого:** 3 коммита, разрез по фиче/модулю, затем тесты.
```

## 5. Выполнение

- После одобрения плана — **автономно**, без подтверждения на каждый `git add`.
- После каждого коммита: `git status --short`.
- В конце дерево должно быть **чистым** (или явно перечислены незакоммиченные
  намеренно).

## Особые случаи

| Статус                            | Что делать                                                                               |
| --------------------------------- | ---------------------------------------------------------------------------------------- |
| `MM` / `AM`                       | есть staged и unstaged части — решить, входит ли unstaged в коммит, не стейджить вслепую |
| `??`                              | добавить / `.gitignore` / удалить; мусор не коммитить молча                              |
| много новых файлов                | крупный коммит допустим, но группировать по областям                                     |
| отладка/локальные конфиги/секреты | назвать отдельно, не прятать                                                             |

## Антипаттерны

| ❌                          | ✅                    |
| --------------------------- | --------------------- |
| Один коммит «всё сразу»     | атомарные коммиты     |
| Резать по типам файлов      | по смыслу/модулю      |
| Коммит ломает дерево        | каждый коммит рабочий |
| Стейдж `git add -A` вслепую | по группам            |
| Мусор/секреты в коммите     | отдельно/`.gitignore` |
| Сообщения не в стиле репо   | свериться с `git log` |

## Чек-лист

- [ ] Статус и `git log` просмотрены.
- [ ] Группы по смыслу, не по типам файлов.
- [ ] Каждый коммит атомарен и оставляет дерево рабочим.
- [ ] Порядок — от фундамента к листьям.
- [ ] План выдан с командами и обоснованием.
- [ ] Секреты/мусор не закоммичены; дерево чистое.
