# Партиционирование

Декларативное партиционирование (PG10+) — для больших таблиц, time-series и
архивации. Это не замена индексам, а способ управлять объёмом и обслуживанием.

## Когда партиционировать

- Таблица очень большая (десятки–сотни млн строк) и растёт.
- Данные естественно сегментируются (по дате, tenant, статусу).
- Нужна дешёвая архивация: `DETACH` старой партиции вместо массового `DELETE`.
- Иначе — преждевременно: партиции усложняют схему и запросы.

## Типы

| Тип   | Ключ                      | Пример                            |
| ----- | ------------------------- | --------------------------------- |
| Range | диапазон (даты)           | `PARTITION BY RANGE (created_at)` |
| List  | перечисление              | `PARTITION BY LIST (status)`      |
| Hash  | равномерное распределение | `PARTITION BY HASH (tenant_id)`   |

## Синтаксис (range по дате)

```sql
CREATE TABLE events (
    id          bigint GENERATED ALWAYS AS IDENTITY,
    created_at  timestamptz NOT NULL,
    payload     jsonb
) PARTITION BY RANGE (created_at);

CREATE TABLE events_2026_01 PARTITION OF events
    FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');
CREATE TABLE events_2026_02 PARTITION OF events
    FOR VALUES FROM ('2026-02-01') TO ('2026-03-01');

-- default-партиция для «вне диапазона» (опционально)
CREATE TABLE events_default PARTITION OF events DEFAULT;
```

- Индексы создаются на родителе и наследуются партициями.
- Наследуемые индексы создаются на каждой партиции; при создании на родителе
  используется `CREATE INDEX ... ON ONLY parent` + отдельно на партициях, либо
  `CREATE INDEX ON parent` (создаст на всех, с блокировками — на проде
  `CONCURRENTLY` по каждой).

## Partition pruning

```sql
-- планировщик читает только релевантные партиции
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM events WHERE created_at >= '2026-02-01' AND created_at < '2026-03-01';
```

- Предикат должен быть по ключу партиционирования (без функций на колонке).
- Prepared statements и generic plans могут мешать pruning — проверять план.

## Обслуживание

- `VACUUM`/`ANALYZE` — по партициям; autovacuum работает per-partition.
- Архивация: `ALTER TABLE events DETACH PARTITION events_2025_01;` (или
  `DETACH ... CONCURRENTLY` в новых версиях) → выгрузка/удаление.
- Новые партиции — создавать заранее (автоматизация/`pg_partman`).

## Ограничения

- Уникальные/первичные ключи должны включать ключ партиционирования.
- Нет «глобального» индекса — только per-partition.
- Много мелких партиций = overhead планирования; разумный размер.
- FK на партиционированную таблицу — ограничения (проверять версию).
- `UPDATE`, меняющий ключ партиции, переносит строку между партициями.

## Антипаттерны

| ❌                                 | ✅                         |
| ---------------------------------- | -------------------------- |
| Партиционировать маленькие таблицы | только большие/растущие    |
| Функция на ключе в запросе         | предикат по ключу          |
| Сотни мелких партиций              | разумный размер            |
| Уникальный ключ без partition key  | включить ключ              |
| `DELETE` старого вместо `DETACH`   | `DETACH`/drop              |
| Не создавать партиции заранее      | автоматизация/`pg_partman` |
